# Backend магазина-витрины

Каталог товаров без корзины и оплаты: PostgreSQL, импорт из xlsx и выгрузки 1С, REST API для фронтенда.

Стек: Node.js 22+ (ESM), Express 5, PostgreSQL 18 (подойдёт любой 12+), драйвер `pg` без ORM, миграции обычными SQL-файлами.

Боевой сервер стоит на том же Windows-компьютере, что и 1С: развёртывание описано в разделе «Разворачивание на Windows». Снаружи сайт доступен через VPS с nginx и WireGuard-туннелем: [docs/vps-reverse-proxy.md](docs/vps-reverse-proxy.md).

## Быстрый старт

```bash
npm install
cp .env.example .env          # при необходимости поправить DATABASE_URL

# БД: любой из двух вариантов
docker compose up -d          # вариант 1: Docker
# вариант 2: Postgres.app, один раз создать роль и базу:
#   psql -d postgres -c "CREATE ROLE shop LOGIN PASSWORD 'shop_dev_password'" -c "CREATE DATABASE shop OWNER shop"

npm run migrate                                  # создать таблицы
npm run import:xlsx -- "БАЗА ДАННЫХ тест для магазина.xlsx"   # тестовые товары и фото
npm run sync:1c -- samples/1c-export.csv         # пример синхронизации: цены и остатки
npm start                                        # публичный API на http://localhost:3000
npm run admin                                    # админка на http://127.0.0.1:3001/admin/
npm test                                         # тесты (в отдельной временной схеме БД)
```

Docker и Postgres.app оба слушают порт 5432. Если нужны одновременно, поменяйте порт в `docker-compose.yml` и в `.env`.

## Разворачивание на Windows

Сервер сайта живёт на том же компьютере, где стоит 1С. Всё локально: база, API, админка и папка выгрузки 1С. Сетевой доставки файлов нет.

Пошаговый список команд для PowerShell: [docs/windows-deploy-checklist.md](docs/windows-deploy-checklist.md). Готовые боевые настройки с плейсхолдерами: `.env.production`. Проверка окружения после настройки: `npm run doctor` (база, папки, порты, незаполненные плейсхолдеры). Архив для переноса собирает `scripts/make-release.sh`. Ниже то же самое с пояснениями.

### 1. Что установить

| Что | Откуда | Примечание |
|---|---|---|
| Node.js 22 LTS | nodejs.org, установщик `.msi` для Windows x64 | Ставит `node.exe` в `C:\Program Files\nodejs`, обёртки в `scripts\windows` ищут его там |
| PostgreSQL 18 | postgresql.org → Download → Windows (установщик EDB) | Нужны только «PostgreSQL Server» и «Command Line Tools». pgAdmin и Stack Builder не обязательны |

Docker Desktop не нужен и на машине с 1С скорее мешает: требует WSL2 или Hyper-V, база внутри контейнера должна успеть подняться до старта задач, лишний слой при диагностике. Файл `docker-compose.yml` остаётся для разработки.

**Если на этом компьютере 1С уже работает на PostgreSQL** (сборка Postgres Pro для 1С, обычно версия 14–16 на порту 5432), есть два пути:

- Использовать тот же кластер: создать в нём роль и базу `shop` (шаг 2), базу 1С не трогать. Проще, но восстановление из `.dump` потребует `pg_restore` той же версии, что и сервер, а из `.sql` пройдёт с двумя безобидными ошибками (см. шаг 5).
- Поставить обычный PostgreSQL 18 на другой порт, например 5433, и указать его в `DATABASE_URL`. Рекомендуется: базы не зависят друг от друга, обновление 1С не задевает сайт.

Если 1С файловая или на MS SQL, ставится PostgreSQL 18 на стандартный порт 5432.

### 2. База и проект

В PowerShell (пароль суперпользователя `postgres` задаётся при установке PostgreSQL):

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -c "CREATE ROLE shop LOGIN PASSWORD 'придумать_пароль'" -c "CREATE DATABASE shop OWNER shop ENCODING 'UTF8'"
```

Проект положить, например, в `C:\shop-backend` (путь без пробелов и кириллицы упрощает жизнь Планировщику):

```powershell
cd C:\shop-backend
npm install --omit=dev
copy .env.example .env
notepad .env
```

В `.env` поменять:

- `DATABASE_URL=postgres://shop:пароль@localhost:5432/shop` (порт 5433, если ставили второй PostgreSQL). Если в пароле есть `@`, `:`, `/` или `%`, их нужно URL-кодировать (`%40` вместо `@`).
- `EXPORT_1C_DIR=C:/1c-export/webdata`: папка, куда 1С выгружает `import*.xml` и `offers*.xml`. Прямые и обратные слэши работают одинаково.
- `UPLOADS_DIR` можно оставить `./uploads`: папка внутри проекта.
- `CORS_ORIGIN`: домен витрины, вместо `*`.
- `ADMIN_HOST`, `ADMIN_PASSWORD`, `ADMIN_ALLOWED_ORIGINS`: см. раздел «Админка». Если админка открывается только с этого же компьютера, достаточно `ADMIN_HOST=127.0.0.1`.

Затем:

```powershell
npm run migrate                     # создать таблицы
npm run sync:1c -- --dry-run        # проверить, что папка выгрузки читается и товары сопоставляются
npm run sync:1c                     # применить
npm start                           # API на http://localhost:3000, Ctrl+C для остановки
```

`npm test` на боевой машине запускать не обязательно, но можно: тесты идут в отдельной временной схеме той же базы и данных не трогают.

### 3. Автозапуск и синхронизация по расписанию

Серверы (API и админка) ставятся как службы Windows через NSSM: стартуют до входа пользователя, перезапускаются при падении, зависят от службы PostgreSQL, логи с ротацией в `logs\`. Синхронизация с 1С и копия базы это задачи Планировщика: они по своей природе разовые запуски по расписанию.

```powershell
cd C:\shop-backend\scripts\windows
Set-ExecutionPolicy -Scope Process Bypass
.\install-services.ps1              # службы ShopCatalogAPI и ShopCatalogAdmin (NSSM ставится через winget)
.\register-tasks.ps1 -Only Jobs     # синхронизация каждые 15 минут и копия базы в 03:00
```

Что лежит в `scripts\windows`:

| Файл | Что делает |
|---|---|
| `sync-1c.cmd` | `npm run sync:1c` по папке `EXPORT_1C_DIR`, вывод в `logs\sync-1c-ГГГГ-ММ.log`, код возврата 1 при ошибке |
| `start-api.cmd`, `start-admin.cmd` | Держат сервер запущенным: если `node` упал, перезапуск через 5 секунд. Логи в `logs\api-*.log`, `logs\admin-*.log` |
| `backup-db.cmd` | `pg_dump` в `backups\shop-ГГГГ-ММ-ДД.dump` и копия `uploads\` в `backups\uploads-ГГГГ-ММ-ДД\`, хранятся 14 последних дампов |
| `install-services.ps1` | Ставит API и админку как службы Windows через NSSM; `-Remove` удаляет |
| `register-tasks.ps1` | Регистрирует задачи в Планировщике: `-Only Jobs` синхронизация и бэкап; `-Only Servers` запасной вариант серверов через `start-*.cmd`, если NSSM использовать нельзя |
| `_common.cmd` | Общие настройки (путь к проекту, `node.exe`, логи), напрямую не запускается |

Регистрация, в PowerShell от администратора:

```powershell
cd C:\shop-backend\scripts\windows
Set-ExecutionPolicy -Scope Process Bypass
.\register-tasks.ps1                                  # синхронизация каждые 15 минут, серверы при загрузке, копия базы в 03:00
.\register-tasks.ps1 -SyncAt "06:05","12:05","18:05"   # вместо интервала: по часам, чуть позже регламентного задания 1С
.\register-tasks.ps1 -Only Sync -SyncEveryMinutes 30   # перерегистрировать только синхронизацию
.\register-tasks.ps1 -Remove                          # удалить задачи
Start-ScheduledTask "ShopCatalog API"; Start-ScheduledTask "ShopCatalog Admin"   # запустить серверы сейчас, не дожидаясь перезагрузки
```

Как это согласуется с 1С. Регламентное задание «Обмен с сайтом» в 1С пишет файлы в `EXPORT_1C_DIR` по своему расписанию. Наша задача запускается по своему и берёт то, что лежит в папке. Если задача стартовала, пока 1С ещё пишет файл, она ждёт, пока размер файла перестанет меняться (до двух минут), и только потом читает. Порядок всегда один: сначала `import*.xml` (названия, описания, привязка к Ид 1С), потом `offers*.xml` (цены, остатки). Повторный прогон по неизменившемуся файлу безвреден: ничего не меняется, в `import_runs` появляется запись с нулём обновлений. Удобнее всего ставить синхронизацию на 5 минут позже выгрузки 1С через `-SyncAt`.

Задачи идут от имени `SYSTEM`, пароль не нужен и вход пользователя не требуется. `SYSTEM` должен читать папку выгрузки: если 1С выгружает в профиль пользователя (`C:\Users\...`), проще в настройках обмена 1С указать общую папку вроде `C:\1c-export`. Другой пользователь задаётся параметром `-User`.

Проверка: `Get-ScheduledTask -TaskName "ShopCatalog*" | Get-ScheduledTaskInfo` показывает время и код последнего запуска, подробности в `logs\`. Если `node.exe` установлен не в `C:\Program Files\nodejs`, задать `NODE_EXE` в системных переменных среды. Для `backup-db.cmd` нужен `pg_dump` в `PATH` либо переменная `PG_BIN=C:\Program Files\PostgreSQL\18\bin`.

Почему NSSM, а не Планировщик или pm2: задача Планировщика «при загрузке» это не служба, ей нельзя сделать `net stop`, она не перезапускает упавший процесс без самодельного цикла и не умеет ждать PostgreSQL. `pm2-windows-service` давно не сопровождается. NSSM это одна утилита без зависимостей, стандартный способ сделать службу из любой программы. `start-*.cmd` и `-Only Servers` оставлены как запасной путь без NSSM.

Файрвол Windows: порт 3000 открывается только для адреса VPS в WireGuard-туннеле, см. `docs/vps-reverse-proxy.md`. Админка на `127.0.0.1` снаружи не видна, это намеренно.

### 4. Перенос текущей базы с машины разработки

В `backups\` лежат (в git не попадают):

- `shop-2026-09-19.dump`: `pg_dump --format=custom`, восстанавливается `pg_restore` версии 18.
- `shop-2026-09-19.sql`: тот же дамп обычным SQL, восстанавливается `psql` любой версии.
- `uploads-2026-09-19.zip`: фото товаров, распаковать в `uploads\` проекта.

Восстановление на Windows в пустую базу `shop` (после шага 2, до `npm run migrate`; таблица `schema_migrations` внутри дампа, поэтому миграции после восстановления ничего не сделают):

```powershell
& "C:\Program Files\PostgreSQL\18\bin\pg_restore.exe" -U shop -d shop --no-owner --no-privileges C:\путь\shop-2026-09-19.dump
# или
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U shop -d shop -f C:\путь\shop-2026-09-19.sql
```

Если сервер PostgreSQL старее 17.6 (например, Postgres Pro для 1С), `.dump` не подойдёт, а при загрузке `.sql` будут две ошибки, которые можно игнорировать: `invalid command \restrict` и `unrecognized configuration parameter "transaction_timeout"`. Данные при этом загружаются полностью.

Проверка после восстановления: `npm run migrate` печатает «Новых миграций нет», `GET /health` отвечает, `npm run sync:1c -- --dry-run` показывает сопоставленные товары.

## Схема БД

Файлы в `migrations/`: `001_init.sql`, `002_external_ids.sql`, `003_manually_edited.sql`.

| Таблица | Назначение |
|---|---|
| `categories` | id, name, slug, parent_id. Дерево категорий, имя уникально в пределах родителя |
| `products` | id, article (уникальный), external_id (Ид 1С), manually_edited, name, description, price (NULL = цена не задана), quantity, category_id, is_active, created_at, updated_at |
| `product_media` | id, product_id (каскадное удаление), url, type (`photo` или `video`), sort_order |
| `import_runs` | журнал импортов: счётчики, ошибки по строкам, артикулы, которых не было в выгрузке |

`updated_at` обновляется триггером при любом изменении строки товара.

**Контракт для админки.** При сохранении названия, описания или категории товара админка обязана ставить `products.manually_edited = true`. После этого синхронизация из 1С перестаёт перезаписывать `name`, `description` и `category_id` этого товара. Цена, остаток и `external_id` обновляются всегда. Чтобы вернуть товар под управление 1С, флаг нужно снять.

## API

Все ответы в JSON, только чтение. Ошибки: `{"error": "текст"}` с кодом 400, 404 или 500.

### `GET /products`

| Параметр | Описание |
|---|---|
| `category` | slug или id категории. Товары вложенных категорий включаются. Неизвестная категория даёт 404 |
| `search` | подстрока в названии или артикуле, без учёта регистра |
| `in_stock` | `true` = только с остатком больше нуля |
| `sort` | `name` (по умолчанию), `-name`, `price`, `-price`, `-updated`. Товары без цены в конце |
| `page`, `limit` | пагинация, по умолчанию 1 и 24, максимум limit = 100 |

```json
{
  "items": [{
    "id": 45, "article": "PL4-18", "name": "Фитинг угловой, 4мм x G 1/8 ...",
    "price": 75, "quantity": 12, "in_stock": true,
    "category": {"id": 1, "name": "Фитинг", "slug": "fiting"},
    "photo": "/media/products/pl4-18-15521efe.jpeg",
    "updated_at": "2026-09-17T12:06:22.476Z"
  }],
  "total": 110, "page": 1, "limit": 24, "pages": 5
}
```

`price: null` означает «цена по запросу». `photo` может быть `null`. Скрытые товары (`is_active = false`) не отдаются.

### `GET /products/:id`

Те же поля плюс `description` и массив `media`: `[{id, url, type, sort_order}]`, отсортированный по `sort_order`.

### `GET /categories`

`{"items": [{id, name, slug, parent_id, products_count}]}`. Плоский список, дерево собирается по `parent_id`.

### `GET /media/...` и `GET /health`

Фото раздаются из папки `uploads/`. Ссылки в API относительные. Если задать `MEDIA_BASE_URL`, они станут абсолютными.

## Админка

```bash
npm run admin        # http://127.0.0.1:3001/admin/
```

Отдельный сервер (`src/admin-server.js`) с правом записи. Публичный API на порту 3000 остаётся только на чтение: эндпоинтов записи и полей `is_active`, `manually_edited` в нём нет, это закреплено тестом. Интерфейс лежит в `admin/`: одна страница на чистом HTML, CSS и JavaScript без сборки.

**Что умеет:** список с поиском и фильтром по категории, карточка товара (название, описание, категория, «показывать на сайте»), загрузка нескольких фото и видео, удаление, порядок перетаскиванием или стрелками. Цена, остаток и артикул показаны только для чтения, ими владеет 1С.

### Эндпоинты записи (только на сервере админки)

| Метод | Путь | Тело | Что делает |
|---|---|---|---|
| POST | `/products` | `{article, name, description?, category_id?, price?, is_active?}` | Создаёт товар, 201 и карточка. Контракт ниже |
| PATCH | `/products/:id` | `{name?, description?, category_id?, is_active?, manually_edited?}` | Меняет поля, возвращает карточку и список `changed` |
| POST | `/products/:id/media` | `multipart/form-data`, поле `files` | Загружает файлы, всё или ничего |
| DELETE | `/products/:id/media/:mediaId` | нет | Удаляет запись и файл с диска |
| PUT | `/products/:id/media/order` | `{"ids": [3, 1, 2]}` | Полный список id медиа в новом порядке |

`GET /products`, `GET /products/:id`, `GET /categories` те же, что в публичном API, но видны скрытые товары и добавлены поля `is_active`, `manually_edited`, `is_linked_to_1c`. В списке работает фильтр `?linked_to_1c=false` (или `true`).

### Подключение отдельного фронтенда админки

Это нужно знать разработчику админки.

**Куда стучаться.** Все запросы админки идут на сервер админки, в разработке это `http://127.0.0.1:3001` (`npm run admin`, порт задаёт `ADMIN_PORT`). Там есть и чтение, и запись: `GET /products`, `GET /products/:id`, `GET /categories`, `POST /products`, `PATCH /products/:id`, медиа. Публичный API на порту 3000 предназначен для витрины: он только на чтение, скрытых товаров и служебных полей в нём нет, для админки он не подходит. Базовый адрес API стоит вынести в настройку фронтенда, в продакшене он будет другим.

**С какого адреса.** Сервер админки принимает запросы из браузера только со страниц, чей origin перечислен в `ADMIN_ALLOWED_ORIGINS` в `.env` бэкенда. Origin это схема, хост и порт из адресной строки: `http://localhost:5173`. Сейчас в `.env.example` вписан `http://localhost:5173`, порт Vite по умолчанию.

```bash
# .env бэкенда, несколько адресов через запятую
ADMIN_ALLOWED_ORIGINS=http://localhost:5173,https://admin.example.com
```

**Если адрес фронтенда другой** (другой порт, `127.0.0.1` вместо `localhost`, `https`, боевой домен), его нужно добавить в `ADMIN_ALLOWED_ORIGINS` и перезапустить `npm run admin`. `http://localhost:5173` и `http://127.0.0.1:5173` это разные origin. При старте сервер печатает список разрешённых адресов. Запись с `*`, путём или без схемы сервер не примет и не запустится.

**Как выглядит отказ.** Если origin не в списке, `POST`, `PATCH`, `PUT` и `DELETE` получают 403 «Запрос с чужого сайта отклонён», а ответы на `GET` браузер не отдаёт странице: в консоли будет ошибка CORS. Оба симптома означают одно: адрес фронтенда не вписан в `.env` или вписан неточно.

**Детали.**

- Preflight (`OPTIONS`) обрабатывается сервером, разрешены методы `GET, HEAD, POST, PATCH, PUT, DELETE` и заголовки `Content-Type`, `Authorization`. Заголовок `Location` из ответа 201 доступен из JavaScript.
- Если на сервере задан `ADMIN_PASSWORD`, каждый запрос должен нести `Authorization: Basic base64(user:password)`. Preflight авторизации не требует. Локально пароль обычно пуст.
- Пути к медиа в ответах относительные (`/media/products/...`). Фронтенду на другом origin нужно подставлять перед ними базовый адрес сервера админки.
- Загрузка файлов: `multipart/form-data`, поле `files`. Заголовок `Content-Type` для неё вручную не задавать, его выставит браузер.

```js
const API = 'http://127.0.0.1:3001'; // из настройки фронтенда
const res = await fetch(`${API}/products`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ article: 'TKC-PY-4', name: 'Тройник' }),
});
if (res.status === 409) { const { code, existing } = await res.json(); /* открыть existing.id */ }
```

### Контракт для разработчика админки: создание товара и привязка к 1С

Новые товары заводятся **только** через `POST /products`. Синхронизация из 1С товары не создаёт никогда, она обновляет существующие.

**Запрос.** `POST /products` на сервере админки (порт 3001), `Content-Type: application/json`.

| Поле | Тип | Обязательно | Правила |
|---|---|---|---|
| `article` | string | да | До 100 символов. Пробелы по краям и двойные пробелы убираются. Хвост складской ячейки 1С вида ` *3*7*34` отсекается. После создания изменить нельзя |
| `name` | string | да | Непустое, до 500 символов |
| `description` | string | нет, по умолчанию `""` | До 20 000 символов, переносы строк сохраняются |
| `category_id` | integer или `null` | нет, по умолчанию `null` | id из `GET /categories` |
| `price` | number или `null` | нет, по умолчанию `null` | Больше 0, округляется до копеек. `null` означает «цена по запросу». Строки и 0 не принимаются |
| `is_active` | boolean | нет, по умолчанию `true` | `false` создаёт товар скрытым с витрины |

Другие поля дают 400. Остаток при создании всегда 0: его и цену дальше ведёт 1С. Фото и видео добавляются после создания через `POST /products/:id/media`.

```bash
curl -X POST http://127.0.0.1:3001/products -H 'Content-Type: application/json' \
  -d '{"article": "TKC-PY-4", "name": "Тройник", "category_id": 3, "price": 1100}'
```

**Ответ 201.** Заголовок `Location: /products/<id>` и карточка в формате `GET /products/:id` админки:

```json
{
  "id": 300, "article": "TKC-PY-4", "name": "Тройник", "description": "",
  "price": 1100, "quantity": 0, "in_stock": false,
  "category": { "id": 3, "name": "Фитинги", "slug": "fitingi" },
  "media": [], "updated_at": "2026-09-18T13:00:00.000Z",
  "is_active": true, "manually_edited": true, "is_linked_to_1c": false
}
```

**Ошибки.** Тело всегда `{"error": "<текст на русском, можно показать пользователю>"}`. У 409 есть ещё `code` и `existing`.

| Код | Когда | Дополнительно |
|---|---|---|
| 400 | Нет `article` или `name`, неверный тип, лишнее поле, слишком длинное значение, несуществующая категория, некорректный JSON | |
| 401 | Включён `ADMIN_PASSWORD`, а Basic-авторизация не передана | |
| 403 | Origin фронтенда не вписан в `ADMIN_ALLOWED_ORIGINS`, см. «Подключение отдельного фронтенда админки» | |
| 409 | `code: "article_exists"`: такой артикул уже есть | `existing: {id, article, name}` |
| 409 | `code: "article_similar"`: артикул отличается от существующего только регистром, пробелами, дефисами или знаками (`fa40` при существующем `FA-40`) | `existing: {id, article, name}` |
| 413 | Тело больше 256 КБ | |

```json
{ "error": "Товар с артикулом «FA40» уже существует", "code": "article_exists",
  "existing": { "id": 261, "article": "FA40", "name": "Монтажный фланец" } }
```

Похожий артикул отклоняется намеренно: два товара с одним мягким ключом 1С не сможет различить, и оба останутся без цены. По `existing.id` можно предложить открыть уже существующую карточку.

**`manually_edited`.** У созданного товара сразу `true`. Синхронизация не перезапишет его название, описание и категорию, но будет обновлять цену и остаток.

**`is_linked_to_1c`.** `true` означает, что товар привязан к записи 1С по её внутреннему Ид. Привязку ставит синхронизация каталога (`import*.xml`), вручную она не задаётся, сам Ид наружу не отдаётся.

- `false` у только что созданного товара. Это нормально до следующей синхронизации.
- Если после синхронизации осталось `false`, то в 1С не нашлось товара с таким артикулом, либо нашлось несколько похожих. Цена и остаток такого товара из 1С **не обновляются**. Такие товары стоит визуально пометить в списке, их отдаёт `GET /products?linked_to_1c=false`.
- Рядом с полем артикула в форме создания нужна подсказка: «Введите артикул точно как в 1С, иначе цена и остаток не подтянутся при синхронизации».

**Как 1С находит товар.** Сначала по Ид 1С, затем по точному артикулу, затем по мягкому ключу. Мягкий ключ игнорирует регистр, пробелы, дефисы, знаки, кириллические двойники латинских букв и разделитель размеров: `tkc-py 4` = `TKC-PY-4`, `SC100*50S` = `SC100X50S`. Опечатка такого рода привязку не рвёт. Другая буква или цифра рвёт. Мягкая пара принимается, только если она однозначна с обеих сторон. Артикул на сайте при привязке не меняется.

**Правила PATCH.** `name` непустой, до 500 символов. `description` до 20 000 символов, переносы строк сохраняются. `category_id` существующей категории или `null`. Неизвестные поля дают 400: цену, остаток, артикул и `external_id` менять нельзя. `manually_edited` поднимается сам, но только если название, описание или категория реально изменились. `is_active` флаг не поднимает. `manually_edited: false` возвращает товар под управление 1С, совмещать его с правкой содержимого нельзя.

**Правила файлов.** Тип определяется по содержимому, а не по расширению: JPEG, PNG, WebP, MP4, WebM. SVG, MOV, HEIC отклоняются с объяснением. Имя файла на диске задаёт сервер. Лимиты в `.env`: `MAX_PHOTO_MB`, `MAX_VIDEO_MB`, `MAX_UPLOAD_FILES`. Первое фото по порядку становится главным в списке товаров. Изменение медиа не поднимает `manually_edited`.

### Безопасность

- По умолчанию сервер привязан к `127.0.0.1` и работает без пароля.
- Для доступа по сети задайте `ADMIN_HOST=0.0.0.0` и `ADMIN_PASSWORD`. Без пароля на внешнем адресе сервер откажется стартовать. Включается HTTP Basic, пользователь `ADMIN_USER`. Трафик не шифруется, поэтому только через VPN или HTTPS-прокси.
- Без пароля сервер отвечает только на имена `localhost`, `127.0.0.1`, `[::1]` и на `ADMIN_ALLOWED_HOSTS`. Это защита от DNS rebinding.
- Изменяющие запросы принимаются только со страниц самой админки (проверка `Origin` и `Sec-Fetch-Site`), CORS выключен. Чужая страница в браузере не сможет слать запросы на localhost.
- Исключение одно: origin из `ADMIN_ALLOWED_ORIGINS`. Это отдельно размещённый фронтенд админки, подробности в разделе «Подключение отдельного фронтенда админки». Запросы без заголовка `Origin` (curl, серверный код) проходят.
- Страница отдаётся с Content-Security-Policy, данные из базы вставляются только как текст.

## Импорт тестовых данных из xlsx

`src/import/xlsx.js`. Читаются только колонки из белого списка: «Наименование на русском», «Артикул», «Розничная цена руб», «фото товара». Себестоимость, контакт продавца, вес и курс юаня не читаются вообще. Файлы `*.xlsx` исключены из git через `.gitignore`.

- Повторный запуск безопасен: upsert по артикулу.
- Встроенные фото сохраняются в `uploads/products/` и привязываются к товару.
- Категория для теста берётся из первого слова названия. Это временно, до реальных категорий из 1С.
- Остатков в xlsx нет, поэтому после импорта `quantity = 0`. Тестовые остатки даёт `samples/1c-export.csv`.

## Синхронизация из 1С

```bash
npm run sync:1c                            # вся папка EXPORT_1C_DIR: сначала import*.xml, затем offers*.xml
npm run sync:1c -- --dry-run               # то же, но базу не менять, только показать
npm run sync:1c -- /path/to/export.csv     # один файл: .csv, .json или .xml; код возврата 1 при ошибке
```

Папка задаётся переменной `EXPORT_1C_DIR` в `.env` (по умолчанию `./site_export/webdata`). 1С и сервер стоят на одной машине, поэтому это локальный путь. Из папки берутся только `import*.xml` и `offers*.xml`, по возрастанию номера (`import0_1`, `import0_2`, ...). Перед чтением каждого файла синхронизация ждёт, пока его размер перестанет меняться: так не читается файл, который 1С ещё пишет. Ошибка в одном файле не мешает обработать остальные, но код возврата тогда 1. Пустая или отсутствующая папка это тоже ошибка, чтобы Планировщик её показал. На Windows запуск по расписанию описан в разделе «Разворачивание на Windows».

Функция `updateFrom1c(pool, file)` в `src/import/update-from-1c.js` (экспортируется и как `update_from_1c`).

- Товар ищется по артикулу. У существующих товаров меняются **только `price` и `quantity`**, всегда и независимо от `manually_edited`.
- Название, описание, категория, фото и видео существующих товаров не затрагиваются.
- Пустая цена или остаток в файле не затирают значение в базе.
- Новые артикулы **не создаются**: товары заводятся только через админку (`POST /products`). Их число выводится в итогах (`notInDb`).
- Товары, которых нет в файле, не меняются. Их артикулы пишутся в `import_runs.missing_articles`.
- Всё в одной транзакции: при ошибке каталог остаётся прежним, попытка пишется в журнал со статусом `failed`.

Формат файла: CSV с разделителем `;`, `,` или табуляция, кодировка UTF-8 или Windows-1251, либо JSON в виде массива или объекта с массивом `products`/`items`. Понимаются числа вида `1 234,50`.

Когда формат выгрузки согласуют, правится только `src/import/parse-1c.js`, в первую очередь словарь `FIELD_ALIASES` с названиями колонок.

### Каталог CommerceML (import*.xml)

```bash
npm run sync:1c -- site_export/webdata/import0_1.xml --dry-run   # показать изменения, базу не трогать
npm run sync:1c -- site_export/webdata/import0_1.xml             # применить
node scripts/report-unmatched.js site_export/webdata/import0_1.xml  # список несопоставленных товаров
```

Тот же вход `updateFrom1c(pool, file, { dryRun })`: файлы `.xml` уходят в `src/import/update-catalog.js`, разбор лежит в `src/import/parse-commerceml.js`. Логика цен и остатков из CSV/JSON при этом не меняется.

- Обновляются только `name`, `description` и категория. Цена, остаток, фото, видео и `is_active` не затрагиваются.
- Пустое описание в 1С не затирает описание в базе. Непустое перезаписывает.
- Товар ищется по `external_id` (Ид 1С), затем по точному артикулу, затем по мягкому ключу артикула (`looseArticleKey` в `src/normalize.js`). Мягкий ключ игнорирует регистр, пробелы, дефисы, знаки, кириллические двойники латинских букв и разделитель размеров: `SC100*50S` = `SC100X50S` = `sc100 50s`. Мягкая пара принимается, только если она однозначна с обеих сторон, иначе пропускается и попадает в отчёт. Артикул на сайте при этом не меняется.
- У товаров с `manually_edited = true` название, описание и категория из 1С не обновляются. Привязка к Ид 1С (`external_id`) обновляется всегда: это идентификация записи, а не контент. Ид сохраняется в `products.external_id`: файл предложений CommerceML (цены, остатки) ссылается на товары именно по Ид.
- В 1С к артикулу дописана складская ячейка: `TKC-PY-4 *3*7*34`. Парсер отсекает хвост вида ` *N*N*N`, на сайт он не попадает.
- Категории берутся из `<Классификатор><Группы>` с вложенностью. Если в классификаторе меньше двух групп, категории не меняются. В текущей выгрузке группа одна («Товар»), поэтому пока действуют тестовые категории из xlsx.
- Пропускаются с записью в журнал: позиции со `Статус="Удален"` или с «НА УДАЛЕНИЕ» в названии, позиции без артикула, артикулы, которые встречаются в файле несколько раз.
- Читаются только Ид, Артикул, Наименование, Описание, Группы, Штрихкод, Статус. Владелец с ИНН, свойство «Поставщик», Изготовитель, реквизиты и налоги не читаются.

### Предложения CommerceML (offers*.xml): цены и остатки

```bash
npm run sync:1c -- site_export/webdata/offers0_1.xml --dry-run   # показать изменения, базу не трогать
npm run sync:1c -- site_export/webdata/offers0_1.xml             # применить
```

Порядок при полной выгрузке: сначала `import0_1.xml` (он привязывает товары к Ид 1С), затем `offers0_1.xml`. Разбор лежит там же, в `src/import/parse-commerceml.js`, обновление в `src/import/update-offers.js`.

- Меняются только `price` и `quantity`, всегда и независимо от `manually_edited`. Название, описание, категория, `external_id`, фото и видео не затрагиваются. Новые товары не создаются.
- Товар ищется по `external_id`, затем по точному артикулу среди товаров без привязки, затем по мягкому ключу артикула, если пара однозначна с обеих сторон. `external_id` при этом не меняется, привязку ставит только каталог.
- Берётся цена одного типа. Если тип в файле один, он и используется. Если несколько, берётся единственный с «розни» в названии, иначе нужно задать `PRICE_TYPE_1C` (название или Ид типа цен) в `.env`. Типы с «закуп», «себестоим», «учётн», «поставщик» в названии не публикуются никогда, даже по явной настройке.
- Цена 0 или отсутствие цены в 1С означает «не назначена». В полной выгрузке цена на сайте сбрасывается в `NULL` («цена по запросу»), в выгрузке только изменений остаётся прежней.
- Остаток берётся из `<Количество>`, при его отсутствии суммируется по складам. Отрицательный остаток становится нулём, дробный округляется вниз.
- Предложения с характеристиками (Ид вида `товар#характеристика`) пропускаются с записью в журнал.
- Читаются только Ид, Артикул, Количество, склады и цена выбранного типа. Владелец с ИНН и цены других типов не читаются.

Повторный `npm run import:xlsx` вернёт товарам длинные названия из xlsx. После перехода на 1С запускать его не нужно.

Примеры файлов лежат в `samples/`. Остатки в них выдуманы, а позиция `DEMO-NEW-001` показывает артикул, которого нет на сайте: он пропускается. Перегенерировать: `node scripts/make-sample-1c.js`.
